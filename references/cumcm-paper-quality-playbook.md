# CUMCM 高质量论文表达手册

本手册用于 P4–P5 论文写作阶段。目标不是增加章节和审计项，而是让已经得到的模型与证据以更高的信息密度、更清晰的因果链和更强的评审可读性呈现出来。

## 1. 评审阅读顺序决定写作顺序

默认假设评审首先看到：

1. 摘要；
2. 问题分析与模型选择；
3. 每问最重要的表图；
4. 每问结论；
5. 模型评价。

因此最重要的信息必须出现在这些位置，而不是埋在算法细节中。

整篇论文应让读者形成一条稳定主线：

```text
题目真正要求什么
→ 为什么当前模型适合
→ 模型如何表示关键结构
→ 得到了什么结果
→ 比简单方案好在哪里
→ 为什么可信
→ 对实际问题意味着什么
→ 边界在哪里
```

## 2. 摘要：优先写“结果”，不是方法目录

摘要不是目录，也不是模型名称集合。

每一问优先使用以下信息顺序：

```text
对象/目标
→ 关键方法
→ 最重要的定量结果
→ 与 baseline 或参考方案的比较
→ 验证方式
→ 适用边界/实际含义
```

如果某问只有一个真正重要的数字，就只写一个；不要为“显得丰富”塞入大量次要指标。

好的摘要句子应类似：

> 针对……，建立……模型。在……条件下得到……；相较……方案，……指标改善……。滚动/压力/敏感性验证表明……，因此该结果适用于……。

禁止：

- 只写“首先、其次、最后建立了某某模型”；
- 把内部工程术语写进摘要；
- 报十几个数字却不说明哪一个回答题目；
- 用“效果显著、性能优异”替代定量比较。

## 3. 问题重述：压缩背景，明确交付

问题重述只保留三类信息：

- 研究对象和现实背景；
- 题面给定条件和数据；
- Q1–Qn 分别要求交付什么。

不要复制题面，不要提前写算法，不要写结果。

## 4. 问题分析：展示“为什么这样建模”

问题分析是高水平论文和普通论文最容易拉开差距的位置。

不要写：

> 问题一采用 ARIMA，问题二采用 NSGA-II……

应该写：

> Q1 的核心矛盾是……；数据具有……特征，而决策时点只能获得……信息，因此需要能够……的模型。Q2 在 Q1 输出基础上还受到……约束，问题本质转化为……。

每一问至少交代：

- 数学对象；
- 关键冲突；
- 最重要约束；
- 数据/机理特征；
- 为什么某类模型合适；
- 与下一问如何连接。

## 5. 模型选择：写成“证据驱动的选择”，不要写成算法介绍

模型选择段建议遵循：

```text
简单 baseline 能解决什么
→ 它暴露什么不足
→ 主模型增加了什么结构
→ 这个结构为什么正好对应题目难点
→ challenger 是否支持保留该复杂度
```

模型名称不需要长篇科普。对于评委熟悉的模型，用 1–3 句说明适配原因即可。

优先比较：

- 题面主指标；
- 可行率/约束；
- 稳定性；
- 解释性；
- 计算代价。

不要为了凑“模型对比”加入输出不一致的方法。

## 6. 公式：只保留决定模型含义的公式

正文公式优先包括：

- 核心目标函数；
- 状态/预测关系；
- 关键约束；
- 评价指标；
- 重要变换或近似。

不必把代码中的每一步翻译成公式。

每个关键公式后立即解释：

- 变量是什么；
- 单位是什么；
- 这一项在现实问题中代表什么；
- 哪个假设或题面条件支持它。

公式之后应该回到问题，而不是连续堆五六个公式不解释。

## 7. 算法部分：写数学求解逻辑，不写工程流水账

算法部分回答：

- 输入是什么；
- 如何初始化；
- 核心迭代/求解逻辑是什么；
- 如何处理约束；
- 停止条件是什么；
- 最终输出如何复核。

不需要正文描述目录结构、脚本文件名、日志系统、manifest 或调试过程。

若流程较复杂，优先用一个简洁算法框或流程图，而不是一页代码。

## 8. 结果部分：每个表图都要有“结论句”

结果部分不应写成：

> 从图 5 可以看出曲线先上升后下降。

应写成：

> 当 X 增加至……后，Y 的边际改善明显减弱；相比 baseline，主模型在高负荷区间将……降低……。这说明……是性能提升的主要来源。

每个核心结果按以下顺序组织：

```text
Headline result
→ baseline/参考比较
→ 原因或机制
→ 实际意义
→ 边界
```

## 9. 图、表、正文三选一

选择依据：

- **表**：读者需要精确比较数字；
- **图**：读者需要看趋势、关系、分布、空间结构或权衡；
- **正文**：只有 1–3 个关键数字，图表反而增加阅读成本。

一个图最好只回答一个主要问题。

图题/表题要告诉读者“比较什么”，正文要告诉读者“结论是什么”。

不要把同一批数据同时做成表和柱状图，除非二者承担不同阅读任务。

## 10. 表格：把最重要的比较放在最容易看的地方

主结果表优先包含：

```text
baseline
主模型
必要 challenger
题面主指标
最关键副指标/约束指标
```

列不要过多。次要诊断放正文、附录或补充图表。

如果主模型只提升 0.3%，但复杂度增加很多，应诚实解释该提升为什么值得，或者回退简单模型。

## 11. 验证：写成“可信度证据”，不要机械列测试

正文只保留最能回答模型风险的验证。

例如：

- 时间预测：时间外/滚动结果优先于训练拟合；
- 优化：可行率、小实例/下界/gap、压力场景优先；
- 评价：权重扰动和删项稳定性优先；
- 机理：边界、守恒、极限情形和敏感性优先；
- 分类：阈值、PR-AUC、混淆矩阵和校准优先。

不要写“经检验模型效果较好”，必须说明检验了什么、结果怎样、是否改变结论。

## 12. 每问结尾：必须直接回答题目

每问最后建议用一个短段落收束：

```text
最终答案/方案是什么
→ 相比 baseline 有什么优势
→ 可信依据是什么
→ 适用条件是什么
→ 后续问使用什么输出
```

评委不应该需要在前面十页中自己寻找答案。

## 13. 模型评价：必须针对“本文这个模型”

优点写：

- 哪个结构正确表达了题目约束；
- 哪个验证证明了稳定性；
- 哪个接口让多问形成统一模型；
- 哪个简化降低了计算成本而没有改变主要结论。

局限写：

- 哪个假设最强；
- 哪种场景未验证；
- 哪个参数最敏感；
- 哪个数据范围限制外推。

禁止模板化：

> 本模型具有较强的准确性、鲁棒性和推广性。

除非后文有对应证据。

## 14. 论文压缩：删过程，留判断

优先删除：

- 无关描述统计；
- 常识性算法介绍；
- 重复公式；
- 调参过程流水账；
- 每张图的视觉复述；
- 代码结构和工程术语；
- 与最终模型无关的失败方案细节。

优先保留：

- 题意转化；
- 关键假设；
- 模型选择理由；
- 核心公式；
- baseline；
- 主结果；
- 最有区分度的验证；
- 实际意义与边界。

## 15. 信息密度检查

写完一个章节后，快速问：

- 这一段有没有新的判断？
- 这个判断有没有证据？
- 这项证据是否回答题面？
- 图表是否比文字更适合？
- 删除这一段会不会损害结论？

如果连续两三段都只是“介绍”，通常应该压缩。

## 16. 最终“评委视角”通读

假设评委只阅读：

```text
摘要
问题分析
每问主结果表/图及图注
每问最后一段
模型评价
```

他应该仍然能回答：

1. 每问解决了什么；
2. 为什么选这个模型；
3. 最重要的结果是什么；
4. 比 baseline 好在哪里；
5. 为什么可信；
6. 有什么实际意义；
7. 在哪里会失效。

如果这七个问题不能回答，优先补叙事和关键证据，而不是继续润色措辞。

## 17. AI 写作的高价值用法

AI 最适合：

- 从冻结证据中提取摘要候选句；
- 比较两种章节结构哪个更清晰；
- 把工程描述改写成数学论证；
- 找出段落中的空话和重复信息；
- 检查术语、单位和跨问表达是否一致；
- 为图表生成“结论导向”图注；
- 站在评委角度指出最难理解的地方。

AI 不应：

- 创造新数值；
- 用没有证据的形容词增强结论；
- 为了语言流畅改变模型边界；
- 把未验证候选模型写成最终模型。

论文质量的核心不是辞藻，而是**第一眼能看懂、关键结论有数字、每个数字有比较、每个比较有解释、每个结论有边界**。
