# 自然语言约束 → 数学规划：约束建模质量手册

> 定位：P1–P4 的优化/调度/资源配置专项手册。用于把题面中的自然语言规则可靠地转换为决策变量、参数、目标、约束和验证。
>
> 来源基础：《数学建模竞赛中的优化模型》中“决策变量和参数—约束—目标函数”的建模框架，以及 CUMCM-2024C 农作物种植策略讲解中“地块/季次/作物兼容 → 确定性规划 → 不确定性 → 关联关系”的结构，经当前工作流质量标准提炼。历史题的具体方案和软件操作不作为通用规则。

## 1. 先建数学对象，不先选求解器

任何优化题先回答：

```text
Sets / Index
Parameters
Decision variables
Derived variables
Objective(s)
Hard constraints
Soft preferences
Uncertainty
Output contract
```

只有这些明确后，才决定 LP / MILP / QP / NLP / DP / network / heuristic。

### 最小表述

| 元素 | 必须说明 |
|---|---|
| 决策变量 | 含义、单位、索引、变量域 |
| 参数 | 来源、单位、是否确定/随机 |
| 目标 | 原始题意、方向、量纲/归一化 |
| 约束 | 题面依据、数学式、硬/软 |
| 输出 | 最终交付表结构和业务含义 |

## 2. Constraint Inventory：先把题面规则列全

不要边写代码边想约束。先建立约束清单：

```text
C01 容量
C02 兼容性
C03 时间/季次
C04 互斥/联动
C05 最低服务/覆盖
C06 轮换/间隔
C07 数量/整数性
C08 风险/情景
...
```

每条至少记录：

- 题面原意；
- 适用索引范围；
- 输入参数；
- 数学表达；
- 程序实现位置；
- 最小测试实例；
- 是否允许 slack。

## 3. 用索引设计表达规模，而不是复制粘贴约束

像“多地块 × 多作物 × 多年份 × 多季次”的题，应先构造集合：

```text
L = 地块集合
C = 作物集合
T = 年份集合
S = 季次集合
```

典型决策变量：

```text
x[l,c,t,s] = 地块 l 在年份 t、季次 s 分配给作物 c 的数量/面积

y[l,c,t,s] = 是否启用该组合（如确有逻辑或固定成本需要）
```

变量设计必须服务真实约束；不要因为“MILP 看起来高级”无意义增加二进制变量。

## 4. 题面自然语言到约束的七类映射

### 4.1 容量约束

例如土地面积、机器工时、库存、预算：

```text
Σ allocation ≤ capacity
```

审计：单位、时间粒度和索引必须一致。

### 4.2 兼容性约束

例如某作物只能在某地块/季节，某任务只能在某设备：

优先使用允许集合 `A ⊂ L×C×S`，避免到处写 Big-M。

```text
(l,c,s) ∉ A  ⇒  x[l,c,t,s] = 0
```

### 4.3 季次/时间结构

如果不同地块可用季次数不同，不要把“年份”当唯一时间索引。

需要区分：

- 单季；
- 第一季/第二季；
- 跨年；
- 先后关系；
- lead time；
- 决策时点可获得信息。

### 4.4 轮作/间隔/连续性

自然语言中的“连续”“至少每 N 年一次”“不能连续种植”等都是跨期耦合，不能靠后处理修补。

典型检查：

- 连续年份是否重复违反；
- 滑动窗口是否满足最低频率；
- 边界年份是否漏检。

### 4.5 分散/集中程度

“不能太分散”“每块面积不宜太小”通常不是自动等价的数学式。

必须先定义可操作指标，例如：

- 最小启用面积；
- 启用地块数量；
- 连片/邻接；
- switch penalty。

并在论文中说明这是对原语义的一个可计算实现，而不是唯一解释。

### 4.6 逻辑约束

“若 A，则 B”“二选一”“至少一个”“至多 k 个”才考虑 0-1 变量。

Big-M 必须：

- 有明确上下界；
- 尽量取紧；
- 记录数值尺度；
- 检查 LP relaxation 是否过松。

### 4.7 销量/需求/服务约束

预测值进入优化时要区分：

```text
forecast ≠ known constant
```

如果上游预测存在误差，下游至少应考虑：

- 场景；
- 区间；
- sensitivity；
- robust/stochastic formulation（题目真正需要时）。

## 5. 从确定性到不确定性的正确升级顺序

推荐：

```text
确定性 baseline
→ 完整确定性约束
→ 找到对参数波动最敏感的地方
→ 场景/区间压力测试
→ 必要时 robust / stochastic
→ 再考虑变量关联或更复杂耦合
```

不要一开始直接使用复杂随机优化。

只有当确定性模型在合理扰动下出现：

- 大量不可行；
- 收益显著下降；
- 服务水平失控；
- 推荐方案频繁改变；

才有充分理由升级不确定性建模。

## 6. 参数关联不是“加一个相关系数”

若价格、销量、成本、产量等存在相关关系，先判断：

1. 题面是否明确要求考虑；
2. 数据是否足以估计；
3. 相关关系如何进入参数生成或情景；
4. 是否会改变方案；
5. 结论对关联结构是否敏感。

不要从样本相关直接写因果机制。

## 7. Baseline 与主模型

优化 baseline 应与最终输出同口径，例如：

- 去年方案/当前方案；
- greedy；
- 每期独立优化；
- LP relaxation；
- 简单确定性规则。

主模型的价值应回答：

```text
baseline 因哪条真实结构失败？
主模型增加哪类约束/耦合？
结果改善多少？
代价是什么？
```

## 8. 求解后必须独立做 Feasibility Audit

求解器返回 `success/optimal` 不能代替业务约束回查。

正式结果至少复核：

- 每条容量约束最大违反量；
- 变量上下界；
- 整数/0-1 变量偏差；
- 兼容性；
- 时间/轮作窗口；
- 总量守恒；
- 服务水平；
- 目标函数重算。

推荐产生：

```text
constraint_id
max_violation
n_violations
worst_index
status
```

## 9. 小实例验证

为复杂规划设计一个人工可核验小实例，例如：

```text
2 地块 × 3 作物 × 2 期
```

能够：

- 手算；
- 枚举；
- 与独立精确算法比较。

重点不是规模，而是证明：变量、约束、目标和结果解释没有写反。

## 10. 不确定性和压力测试

优先扰动最可能改变决策的参数：

- demand；
- yield；
- price；
- cost；
- capacity；
- failure probability。

不要机械所有参数 ±5% / ±10%。

需要回答：

- 推荐方案是否改变；
- 可行率是否下降；
- 目标值/服务水平变化；
- 哪个约束开始绑定；
- failure threshold 在哪里。

## 11. 论文写法

优化模型正文应优先包含：

1. 决策变量；
2. 目标；
3. 最关键约束及现实含义；
4. 求解方法；
5. baseline；
6. 可行性/最优性证据；
7. 最终方案；
8. 不确定性或失败边界。

不要把篇幅花在求解器按钮、软件界面或标准算法教科书说明上。

## 12. 历史案例如何使用

CUMCM-2024C 在本手册中只用于提炼以下可迁移结构：

```text
多类型资源
+ 多时间/季次
+ 兼容规则
+ 跨期规则
→ 确定性规划
→ 参数不确定性
→ 变量关联/情景
```

不得把历史题中的具体作物、地块或解法当作新题默认模型。
