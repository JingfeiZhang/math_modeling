# 参考算法模板编写规范

本规范适用于 `代码库/` 的离线示例。模板是 **study-only 的教学/原型资产**，不是当前赛题 Formal 实现。正式使用须遵守：

- `references/algorithm-sources/QUALITY_STANDARD.md`
- `references/competition-knowledge/playbooks/academic-quality-standard.md`

进入比赛项目后必须重新建立题面接口、数据/单位、baseline、约束、验证和证据输出。

## 1. 模板的合格标准

一个高质量模板应帮助快速回答：

- 实际运行的算法身份是什么？
- 它解决什么数学/统计结构？
- 什么情况下应使用 / 不应使用？
- 输入和输出的语义、形状、顺序与单位是什么？
- 关键假设与风险是什么？
- 合理 baseline 是什么？
- 最有信息量的验证是什么？
- 失败时如何显式返回或回退？
- 如何迁移成当前项目的 Candidate？

模板不负责证明算法“优秀”，也不生成可直接写入论文的结果。

## 2. 文件头建议

```python
# -*- coding: utf-8 -*-
"""
<算法中文名> / <English name>

Method identity
    实际算法/求解器名称。
Purpose
    解决什么数学或统计问题。
Use when
    数据结构、变量类型、目标和约束满足什么条件。
Do not use when
    至少列出常见不适用情形。
Assumptions
    关键统计/数学/机理假设。
Input contract
    形状、语义、单位、排序/分组/时间边界要求。
Output contract
    主结果、状态、诊断和必要不确定性。
Baseline
    同输出的简单比较对象。
Validation
    最值得做的任务专项验证。
Known failure modes
    泄漏、不可行、局部最优、尺度敏感、不可辨识等。
Dependencies
    numpy / scipy / ...

注意：本文件为离线示例，示例数字和图不是比赛证据。
"""
```

禁止只写“适合 C 题”“精度高”“比赛常用”“创新加分”等无法验证的标签。

## 3. 核心函数与演示分离

- 核心算法必须函数化；
- `if __name__ == '__main__':` 只做最小 study-only 示例；
- 不在 import 时产生文件、图或训练任务；
- 关键错误抛出可理解异常，不静默吞掉；
- 尽量把数据读取与算法逻辑分离，便于在当前项目重写接口。

## 4. 优先返回结构化结果

不要只 `print()`。建议至少能够表达：

```python
{
    "method": "...",
    "status": "ok | failed | fallback",
    "result": ...,
    "metrics": {...},
    "diagnostics": {...},
    "seed": ...,
    "warnings": [...],
}
```

具体字段可按方法变化，但调用方必须知道：算法是否成功、实际运行了什么、主结果是什么、哪些诊断失败、有无随机性或 fallback。

## 5. 输入输出合同

至少写清：

- 行/列/节点/时间步分别代表什么；
- 是否要求排序、非负、整数、平稳、标准化；
- 缺失值如何处理或是否允许；
- 输出对应题面哪类量；
- 求解失败/未收敛/不可行时如何表示；
- 主指标方向和单位（若有）。

不要用“传入数据即可”代替接口说明。

## 6. 示例数据只演示 API

允许手写小数组或固定随机种子生成示例；禁止联网取数。示例目标是理解接口和算法行为，不是模拟竞赛真实数据。

统一提示：

```text
阅读真实题面和数据字典
→ 在当前项目中建立数据接口与单位合同
→ 重写本模板核心逻辑
→ 建 same-output baseline
→ 使用项目自己的切分、指标、约束和验证
```

不得再写“把示例数据换成附件即可”“改参数即用”。

## 7. 禁止 silent fallback

若原方法缺少依赖或运行失败，不能静默换成另一算法并继续使用原名称。

例如：

```text
TensorFlow 缺失
→ 自动用 MLP
→ 仍输出 LSTM
```

是不允许的。

正确做法：

- 明确报错并提示依赖；或
- 显式返回 `fallback_method=...`；
- 把 fallback 作为另一个模型身份独立比较。

算法身份变化必须可见。

## 8. 数据处理边界

模板可演示预处理，但必须强调：

- scaler/encoder/imputer 只能在训练数据拟合；
- 时间序列保持时间方向；
- panel/组数据保持主体边界；
- target encoding 必须在折内或训练窗口内；
- 不为树模型机械标准化；
- 不为分布“好看”机械删除真实极端值；
- 多表合并前后检查行数和重复。

示例处理流程不能直接成为 Formal pipeline。

## 9. 随机性与复现

含随机性的算法必须：

- 接受 `seed/random_state`；
- 尽量使用局部随机数生成器；
- 不只展示最好一次；
- 能记录多种子结果；
- 比较算法时支持公平计算/函数评估预算。

## 10. Known-answer / sanity check

适合的方法应尽量附一个微型验证：

- 人工可算；
- 穷举可比；
- 有解析解；
- 可由精确 solver 验证；
- 可检查守恒、约束或单调性。

known-answer 的价值通常高于再增加一个展示图。

## 11. 参数与调优说明

参数说明应回答：

- 参数控制什么数学行为；
- 合理范围来自哪里；
- 哪些参数最敏感；
- 调参使用什么验证数据；
- 什么情况下停止继续调。

禁止“多试几个取最高分”“参数越大越好”式说明。

## 12. 指标与 baseline

模板可以演示指标，但必须说明边界，例如：

- MAPE 遇零值可能失真；
- Accuracy 在严重不平衡分类中可能误导；
- R² 高不等于预测能力强；
- silhouette 高不自动等于簇有现实意义。

README 应提供合理 baseline。模板不得输出脱离上下文的“优秀/良好/通过”评级。

## 13. 优化与求解状态

优化模板至少显式返回或打印：

- solver / search status；
- 可行性；
- 目标值；
- 关键约束残差；
- gap/bound（若可获得）。

整数问题不得把连续解四舍五入后直接当作最优整数解。

## 14. 可视化

模板图只用于学习/诊断，不自动成为 Paper Evidence。

- 默认无界面安全；
- 图回答明确关系；
- 轴标签包含变量与单位（示例单位则明确）；
- 不强制每个模板画图；
- 不使用装饰性 3D、彩虹色或复杂图形暗示模型更高级。

正式论文图必须由主工作台的 Figure Data Manifest → Visual Intent → Figure Brief → render/QA 流程从真实 artifact 重新生成。

## 15. 兼容与依赖

模板环境由 `代码库/requirements.txt` 管理，与根 `environment.yml` 隔离。不要为了让历史模板运行而修改主工作台依赖。

不得通过未声明的语义变化或 fallback 掩盖依赖不兼容。

## 16. Formal 前必须重写

从模板选中方法后，在当前项目里重新完成：

```text
题面接口
+ 数据/单位/变量角色
+ same-output baseline
+ 目标/约束/算法身份
+ 切分/随机种子
+ known-answer
+ 题型专项验证
+ artifact 输出
+ 代码/数据/环境记录
```

必须删除或重新论证模板中的：示例数据、示例阈值、默认业务解释、不适用指标、静默 fallback、与真实时间/空间边界不一致的切分。

模板完成的标准不是“脚本能运行”，而是**方法身份清楚、接口可迁移、失败可见、验证可设计**。
